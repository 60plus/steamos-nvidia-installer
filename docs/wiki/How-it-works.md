# How it works

This page explains the implementation for contributors. For installation steps,
use [Build the USB image](Build-the-USB-image.md) and
[Install and first boot](Install-and-first-boot.md).

## What the project changes

The starting point is Valve's recovery image. The builder makes a separate copy,
adds NVIDIA support and project tools, and adjusts the recovery installer.
SteamOS, Steam, Gamescope and the A/B partition layout remain their upstream
components. This project does not provide a separate Linux distribution or its
own replacement OS updater.

The original image-building and self-healing approach comes from
[28allday/steamos-nvidia-installer](https://github.com/28allday/steamos-nvidia-installer).
This project extends it with desktop tools, validation, device handling and tests.

## Building the USB image

`steamos-nvidia-installer.sh` coordinates the build. It mounts the image through
loop devices, reads the exact SteamOS kernel version and resolves a driver package
version. The selected package URLs are pinned in `driver.conf` so a later OS
repair does not silently select a different NVIDIA release.

The builder uses an isolated build root to compile NVIDIA's open kernel modules
against that kernel. It copies the required userspace libraries into the image,
checks them with the target's loaders and generates the boot files. The 32-bit
checks are for 32-bit games and their runtime dependencies on a 64-bit OS.
`--trim-cuda` removes compute libraries; it does not switch the OS to another
architecture. Package caches speed up repeated builds, but cached output still
has to match the selected inputs.

The build adds installation shortcuts and records image provenance. The source
image is retained. A successful shell syntax check is not proof that an image
boots or a game renders correctly; those are separate tests.

## Installation and USB disks

`scripts/install-target.py` discovers candidate disks and excludes the running
installer's disk. It distinguishes external USB targets from internal disks and
checks the selected target before handing work to the recovery installer.
Fresh installation erases the selected disk. Reinstallation preserving home
expects an existing compatible SteamOS layout.

`scripts/patch-repair.py` adjusts the recovery script. The narrow installer
permission helper allows only the installation operation that requires it;
ordinary installed-system administration still uses the user's password.
External USB installation uses the same OS layout. Moving that installation
between unrelated PCs is a separate compatibility question.

## The A/B slots

SteamOS maintains two system partition sets, A and B. Each has rootfs, EFI and
var partitions. The shared home partition holds user data, including games and
saves. The boot configuration selects which set will run next.

| Term | Meaning |
|---|---|
| Active slot | The system currently running |
| Inactive slot | The other system set, available for preparation |
| Selected slot | The set requested for the next boot; it can differ from active |
| Shared home | User data shared across boots of either set |

A and B are interchangeable. Code uses SteamOS partset links such as `self` and
`other`, rather than assuming that B is always the update target. Device checks
must resolve to different block devices before writing.

An update replaces the inactive system. It does not create an unlimited history
of snapshots. A later OS update or driver change can overwrite the previous
system. Switching slots does not revert shared home data, saves or every user
setting. Valve's migration also handles settings between the system sets.

## Updates installed by Steam

The hook supports the inspected `steamos-bootconf` activation formats and the
SteamOS 3.9 Preview `holo-bootconf` format, retaining Valve's activation mode.
Repair runs before activation, with the inactive slot marked invalid and its
retry counters cleared. Unknown formats are rejected rather than patched by
approximate matching. Channel selection is separate: normal builds keep the
original channel; `--experimental-beta` and `--experimental-preview` explicitly
select their respective channels.

In the inspected Preview handler, Valve tries its supported finalizer names
before activating the slot. Its shutdown service subsequently catches up
changes in `/etc` and `/var` and completes configuration migration. The NVIDIA
hook preserves that sequence and repairs `/usr` before activation. Preview's
`steamos-update` alias points to `holo-update`; the installer saves a regular
copy of that native executable before installing its wrapper.


Valve downloads and stages the new OS. The shared RAUC completion hook invokes
`repatch.sh`, generated by the builder, before the update can be accepted.
The repair builds the pinned NVIDIA driver for the new kernel, installs its
libraries and restores project integrations in the new root.

Validation includes kernel/module compatibility, project file checksums,
userspace library dependencies and available space. A completion marker records
an accepted result. Failures keep the staged system disabled instead of treating
a downloaded OS as ready merely because the download finished.

Before the final free-space check, the repair helper can reclaim unused Btrfs
metadata allocation in the inactive slot. It runs only below the 256 MiB reserve,
with at most four filtered passes of one metadata block group each. It preserves
files and redundancy profiles, synchronizes the filesystem and measures space
after each pass, including partial failures. An unrecovered shortage still stops
slot activation. See the [Btrfs balance documentation](https://btrfs.readthedocs.io/en/latest/btrfs-balance.html).

The hook uses a separate mount namespace with one-way (`slave`) propagation.
Systemd automounts, including EFI and ESP, remain visible inside it. Mount changes
made by the hook do not propagate back to the host. Temporary `noatime` settings
protect Valve's migration from writes to a frozen filesystem. These settings are not a permanent change to the user's
filesystem mount policy. The `steamos-update` wrapper and shared hook cooperate
so supported update entry points receive the same repair step.

## Changing the NVIDIA driver

The desktop driver manager separates selection from preparation:

1. `driver-manager.py` presents available releases and GPU compatibility hints.
2. `driver-change.py` resolves the selection, checks OS/update state and records
   a private transaction request.
3. `driver-stage.sh` copies the current system into a temporary Btrfs image,
   gives it a new filesystem identity and validates the intended target.
4. The inactive boot entry is disabled before its root filesystem is overwritten.
5. Valve's migration and the repair hook prepare and validate the selected driver.
6. Only success permits selection of the prepared slot for restart.

A compatibility hint is not a completed test on every GPU. The manager uses
NVIDIA's open kernel driver path; GTX 10-series and older architectures are
outside that path. The tool does not convert the install to a legacy proprietary
kernel driver.

## Updating installer tools from releases

**SteamOS NVIDIA Installer Update** applies project integration files without a
new USB installation. It is included only when the builder receives a release
source configuration. Public builds are intended to use GitHub releases with a
production signing key. A source must be configured explicitly; an unavailable
server does not cause a switch to another source.

The source configuration contains an API URL, download origin, channel policy
and public verification key. The private signing key is not included. The release
packer creates a bundle, a manifest and an Ed25519 signature. The manifest names
the integration version, supported SteamOS versions and SHA-256 file hashes.

The updater verifies the signature, archive checksum and file hashes, rejects
unexpected paths and links, and limits download size. It accepts a fixed list of
project files rather than arbitrary filesystem replacements. Confirmation pins
the manifest digest so a changed release must be checked again.

Integration updates share the driver's transaction lock, staging mechanism and
rollback record. They retain the selected NVIDIA driver and verify it rather
than rebuilding it unnecessarily. New helpers and policies are applied to the
inactive root. The old image build metadata is preserved; a separate
`integration-version.json` records the current tools version.

This mechanism cannot deliver every possible change to image building or disk
layout. Such changes may still need a new installer. See
[Installer updates](Installer-Updates.md) for the user workflow.

## Recovery and interrupted work

Preparation marks the target invalid before writing. The current system is
retained, so interrupted preparation can be retried from the working slot.
The desktop rollback action verifies that the saved transaction still describes
both systems before selecting the previous slot. It refuses stale rollback after
another operation has replaced the relevant files or OS version.

This is validated manual recovery, not a promise of automatic rollback after any
failed boot. Power loss at different stages, firmware behavior and hardware
failures need separate coverage. Keep recovery media available.

## Display and Bluetooth helpers

- `hdr-defaults.py` initializes new Steam display profiles with HDR off before
  Steam starts. It preserves existing choices; it is not a permanent HDR ban.
- `safe-graphics.py` provides an optional recovery mode requesting conservative
  output settings. It does not replace the graphics driver or guarantee a fix for
  every compositor artifact.
- `bluetooth-resume.py` attempts reconnection for relevant Bluetooth audio after
  resume. Reconnection support is different from waking the PC with a controller.
- Controller support uses the stock stack by default. Optional xpadneo is built
  and checked separately when enabled. Its Bluetooth profile and module changes
  can affect how Steam sees a controller, so it is not required for all pads.

## Performance overlay

An image built with all components in the [build guide](Build-the-USB-image.md#complete-build) includes the corrected MangoApp. Custom builds add it
with `--mangoapp-dir`. It is built from a pinned MangoHud revision with
an upstream fix that refreshes NVIDIA sensor settings on each sampling cycle.
A second patch hides unsupported NVIDIA voltage and junction temperature fields.
It does not fabricate sensor values or change the NVIDIA driver.
Steam overlay levels 3 and 4 also show the active renderer model, its dedicated
VRAM capacity when available, and the CPU model reported by Linux. Smaller
overlay levels keep their original layout. Hardware names are detected at
startup; they are not taken from the computer used to build the image.

`tools/build-mangoapp.sh` builds the executable in a disposable SteamOS build
root. The artifact contains the binary, a checksum and source metadata, and the
MangoHud license. `--mangoapp-dir` includes these files in an image or a signed
integration package. A build without that option keeps the stock overlay.

Installation checks the artifact checksum and resolves its runtime libraries in
the target root before creating a systemd user service override. The override
starts the corrected binary from `/usr/lib/steamos-nvidia`; the distribution's
binary is preserved. The OS repair hook copies the artifact to the next slot and
checks it again. An incompatible artifact fails preparation instead of silently
installing an unusable overlay.

## Capture-color correction

An image built with all components in the [build guide](Build-the-USB-image.md#complete-build) includes this separately maintained backport.
Outgoing Remote Play has passed hardware testing; screenshot formats still need
separate acceptance. Custom builders supply the artifact with `--gamescope-dir`.

A separate Gamescope build backports an upstream NVIDIA capture correction to
version 3.16.23.4. It checks whether the Vulkan device supports the 10-bit RGB
format required for capture. When that format is unavailable, it uses the
supported BGR layout and decodes screenshot channels in the matching order.
The shared capture pool also requests sampled-image usage: the RGB-to-NV12
shader reads these textures. Missing that usage can produce black video even
when the local game renders normally.
This targets swapped red and blue in PipeWire capture, including Remote Play,
and AVIF screenshots. It does not change the monitor mode, HDR defaults, kernel,
or NVIDIA driver, and is not a fix for HDMI HDR failures.

`tools/build-gamescope.sh` builds from a pinned source revision in a disposable
stable build root. The output contains a staged installation tree, source and
patch metadata, checksums and license notices. It does not replace Gamescope on
the running system. The image builder accepts it through `--gamescope-dir`.

The binary lives under `/usr/lib/steamos-nvidia/gamescope/bin`, leaving the
package-managed binary intact. A user service drop-in selects it through PATH
only on SteamOS 3.8.16 with Gamescope 3.16.23.4-1 and the expected session script.
The installer verifies its source revision, hash and target library resolution.
Recovery 3.8.14 keeps the stock binary. The A/B repair hook carries the artifact
into the updated slot and reevaluates compatibility before activation. A future
or unsupported version returns to stock Gamescope automatically.

Installer Update preserves an already installed artifact and reevaluates this
policy; it does not currently distribute a new Gamescope artifact. Diagnostics
include the selected status and session environment. The shipped-file checksum
manifest covers the capture binary, provenance and licenses. Generated status
and the version-dependent service selection are excluded because they change
when an OS update activates the backport or returns to stock. Physical capture tests are
still required before treating the correction as verified on a particular GPU.

For a contribution, describe the failing behavior and how to reproduce it, link
the relevant issue, identify the affected entry point and explain the validation.
Keep changes to display policy, driver selection and disk operations separately
reviewable. Report VM and physical hardware results separately. Do not remove
upstream authorship or licensing when reorganizing code.

## Remote Play receiving and color formats

Receiving a stream from another PC uses Steam's decoder and renderer. This is
separate from Gamescope's PipeWire capture path used when sending a stream.
Fixing capture does not automatically fix playback in the other direction.

The NVIDIA VAAPI decoder exports decoded frames for Vulkan to import. The exported
memory layout and plane descriptors must agree with the format selected by Steam.
NV12 stores interleaved U/V chroma; NV21 reverses that order. The correction changes
the exported NV12 chroma-plane DRM descriptor from RG88 to GR88 so its byte order
matches the data. A wrong descriptor can corrupt video colors while the receiver's menu remains correct.
The receiver artifact included by the complete build in the [build guide](Build-the-USB-image.md#complete-build) corrects the NV12 chroma descriptor and exports a
single memory object, which Steam's Vulkan importer requires. Build it with
`tools/build-remote-play.sh` and include it with `--remote-play-dir`.

The artifact lives under `/usr/lib/steamos-nvidia/remote-play`. Steam's user service
loads a small environment helper with matching 32-bit and 64-bit libraries. The
64-bit helper checks the executable name and applies the decoder settings only
to `streaming_client`; it does not alter Steam's installed files. Existing preload
entries are preserved. Other applications keep their decoder and display settings.
The receiver uses SDR because its X11 display detection can select HDR10 even when
Game Mode HDR output is off. This does not disable HDR for local games.

The repair hook copies and verifies the artifact in the updated A/B slot and
recreates the service configuration. Installer Update does not yet distribute this
optional binary artifact. To disable the receiver policy for diagnosis, set
`STEAMOS_NVIDIA_REMOTE_PLAY=0` in a user override for `steam-launcher.service`, then
restart Game Mode. Hardware testing is required after installing a new image.

## NVENC encoding from a 32-bit Steam host

RTX 50 hardware can encode video, but NVIDIA's 32-bit CUDA interface cannot use
these GPUs. The NVENC bridge included by the complete build in the [build guide](Build-the-USB-image.md#complete-build) provides a VAAPI encoder to the 32-bit Steam
host. Frames pass through shared memory to a 64-bit helper, which runs CUDA and
NVENC, then returns H.264 or HEVC bitstreams. Steam therefore reports VAAPI HEVC
or VAAPI H264 even though encoding is performed by NVIDIA hardware.

The artifact is stored in `/usr/lib/steamos-nvidia/nvenc`. Its 32-bit driver is
installed at `/usr/lib32/dri/nvidia_drv_video.so`. The user service
`steamos-nvidia-nvenc.service` starts with `steam-launcher.service` and uses a socket
inside the user's runtime directory. No network listener or root daemon is added.
Steam can fall back to software encoding if the optional service is unavailable.

The 64-bit receiver keeps its separate decoder and NV12 color correction. The
encoding bridge does not change receiver HDR policy or add HDR streaming support.
The repair hook copies the private artifact into the new A/B slot, verifies its
hashes and loader dependencies, then recreates the driver, service and Steam drop-in.
The addon manifest covers those files. Installer Update does not yet distribute
this optional binary artifact to systems built without it.

Device testing on RTX 5060 confirmed HEVC SDR encoding, reconnect and automatic
helper startup after reboot. A fresh installation followed by the 3.8.14 to 3.8.16
OS update preserved the packaged bridge and service. Encoding also worked after
deep suspend/resume. Other GPUs and later OS updates require their own validation.


## Windows build helper

`tools/build-on-windows.ps1` connects to an existing Linux build VM over SSH and
runs the same image builder. It quotes paths and options for the remote shell,
uses the normal interactive SSH/sudo authentication and propagates failures.
It does not create a VM, distribute a recovery image or replace package checks.

Before the build, `tools/check-build-host.sh` checks tools, local filesystem type
and space. Its temporary loop-backed Btrfs image and OverlayFS write test run in
a private mount namespace. Cleanup removes only its own temporary probe after
unmounting and detaching; failed cleanup retains the directory for inspection.
See [Build on Windows](Build-on-Windows.md) for setup and validation limits.


## Complete image build

`tools/build-complete.sh` opens the original 3.8.14 recovery image with a read-only
loop device. It mounts rootfs-A read-only with log replay disabled, then uses a
separate writable OverlayFS layer for build dependencies and compilation. The
original image is not the build root's writable filesystem.

The four existing component builders run in order. Once all succeed, the wrapper
stops background processes rooted in that build environment, unmounts it and
discards its compilation layer, then invokes the
normal installer with every artifact and updater source. A failure prevents later
stages from running. The output checksum is only generated after the installer
returns successfully. See [Complete build](Build-the-USB-image.md#complete-build)
for defaults, space requirements and the current validation scope.
